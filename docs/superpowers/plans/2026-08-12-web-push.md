# Web-Push im Browser · Implementierungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Erinnerungen erreichen den Browser. Der Schalter in den Einstellungen registriert ein echtes Push-Abo, und `reminder-worker` liefert daran aus.

**Architecture:** Die Serverseite existiert vollständig und läuft fehlerfrei — `pg_cron` treibt `reminder-worker` jede Minute, die Trigger auf `events` bauen die Jobs. Es fehlt ausschließlich die Client-Seite: ein Service Worker, ein Push-Abo und die Zeile in `push_subscriptions`.

**Tech Stack:** TypeScript strict, React 19 + Vite, Vitest, Web Push (VAPID), Supabase.

## Ausgangslage, geprüft am 2026-08-12

| Befund                                                                     | Folge                                                                |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `ralia-reminder-worker` läuft jede Minute; 36 gesendet, 0 Fehler           | die Pipeline ist gesund, sie wird nicht angefasst                    |
| `push_subscriptions` hat die Policy `auth.uid() = user_id` für ALL         | der Client darf sein eigenes Abo anlegen — **keine Migration nötig** |
| `vapidPublicKey` kommt bereits aus `/config` in den `BootContext`          | der Schlüssel ist da, er wird nur nicht benutzt                      |
| Im neuen Client registriert **nichts** ein Push-Abo                        | genau das baut dieser Plan                                           |
| `clearLegacyServiceWorker()` meldet **alle** Service Worker ab             | würde unseren eigenen sofort wieder töten, siehe Task 1              |
| Der Payload verweist auf `/icons/icon-192.png` — die Datei existiert nicht | Icons gehören dazu, siehe Task 4                                     |
| Die 29 vorhandenen Abos stammen aus Ralia 1.x                              | sie bleiben gültig; unsere Abos kommen dazu                          |

**Der Payload steht fest.** `reminder-worker` sendet:

```json
{
  "title": "⏰ Erinnerung: <Terminname>",
  "body": "12. Aug. 2026, 09:00 • <Ort>",
  "icon": "/icons/icon-192.png",
  "badge": "/icons/icon-192.png",
  "tag": "event-reminder-<eventId>-<datum>-<offset>-<userId>",
  "data": { "url": "/", "eventId": "…", "source": "event-reminder", "…": "…" }
}
```

Der Service Worker muss genau diese Form verarbeiten. Sie wird **nicht** geändert — die
Serverseite bleibt unberührt.

- Nach jedem Task: `npm run verify` grün.

- [ ] **Step 3: Die Funktion schreiben**

Create `packages/core/src/push/vapid.ts`:

```ts
/**
 * base64url → Bytes, wie `pushManager.subscribe` den `applicationServerKey`
 * verlangt.
 *
 * `/config` liefert den VAPID-Schluessel als base64url ohne Fuellzeichen. Ein
 * Fehler hier aeussert sich im Browser als `InvalidAccessError` ohne
 * verwertbare Meldung — deshalb wird hier gepruefte Arbeit geleistet und nicht
 * an der Aufrufstelle improvisiert.
 */
export function urlBase64ToUint8Array(base64Url: string): Uint8Array {
  const padding = '='.repeat((4 - (base64Url.length % 4)) % 4);
  const base64 = (base64Url + padding).replace(/-/g, '+').replace(/_/g, '/');
  const raw = atob(base64);
  const bytes = new Uint8Array(raw.length);
  for (let index = 0; index < raw.length; index += 1)
    bytes[index] = raw.charCodeAt(index);
  return bytes;
}
```

und dieselbe Zeile — über `./push/index.js` — in `packages/core/src/index.ts`.

- [ ] **Step 1: Den Service Worker schreiben**

Create `apps/app/public/sw.js`:

```js
/*
 * Ralia Service Worker — ausschliesslich fuer Push.
 *
 * Er cached NICHTS. Ein cachender SW ist genau das Problem, gegen das
 * clearLegacyServiceWorker() im Boot geschrieben wurde: der alte SW von
 * Ralia 1.x beantwortete Anfragen aus altem Bestand, und die App sah
 * Geisterdaten. Es gibt hier deshalb bewusst kein `fetch`-Ereignis.
 */

self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (event) =>
  event.waitUntil(self.clients.claim()),
);

self.addEventListener('push', (event) => {
  if (!event.data) return;

  let payload;
  try {
    payload = event.data.json();
  } catch (error) {
    // Ein unlesbarer Payload darf keine leere Benachrichtigung erzeugen.
    return;
  }

  const title = payload.title || 'Ralia';
  event.waitUntil(
    self.registration.showNotification(title, {
      body: payload.body || '',
      icon: payload.icon || '/icons/icon-192.png',
      badge: payload.badge || '/icons/icon-192.png',
      // Der tag verhindert, dass dieselbe Erinnerung mehrfach stehen bleibt.
      tag: payload.tag || undefined,
      data: payload.data || {},
      ...(payload.options || {}),
    }),
  );
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  const target =
    (event.notification.data && event.notification.data.url) || '/';

  event.waitUntil(
    self.clients
      .matchAll({ type: 'window', includeUncontrolled: true })
      .then((windows) => {
        // Ein offenes Fenster wird nach vorn geholt, statt ein zweites zu oeffnen.
        for (const client of windows) {
          if ('focus' in client) return client.focus();
        }
        return self.clients.openWindow(target);
      }),
  );
});
```

Reihenfolge zählt: erst deaktivieren, dann abmelden — bricht es dazwischen ab, ist lieber
eine tote Zeile in der Datenbank als ein Abo, das der Server weiter bedient.

Jeder Fehlerpfad endet in einem Zustand, den die Oberfläche zeigen kann. Kein `throw` nach
