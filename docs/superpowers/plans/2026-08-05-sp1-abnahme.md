# SP1 — Abnahmeprotokoll

**Datum:** 2026-08-05
**Spec:** [../specs/2026-08-05-sp1-auth-partner-design.md](../specs/2026-08-05-sp1-auth-partner-design.md)
**Plan:** [2026-08-05-sp1-auth-partner.md](2026-08-05-sp1-auth-partner.md)

Durchgang durch die zwölf Abnahmekriterien. Geprüft wurde gegen den
Preview-Build, die Browserprüfungen in echtem Chromium über Playwright.

**Kein Test hat sich registriert oder angemeldet.** Das wäre ein Schreibzugriff
auf die Produktionsdatenbank. Wo eine echte Anmeldung nötig ist, steht der Punkt
unten als Umgebungsprüfung — offen und nicht stillschweigend als erledigt
verbucht.

## Ergebnis

| #   | Kriterium                                                       | Befund                         |
| --- | --------------------------------------------------------------- | ------------------------------ |
| 1   | `verify` fehlerfrei, `e2e` grün                                 | **erfüllt**                    |
| 2   | Wache leitet um, Ziel bleibt erhalten                           | **erfüllt**                    |
| 3   | Registrieren zeigt den Bestätigungshinweis, ohne Sitzung        | **teilweise** — Postfach nötig |
| 4   | `type=recovery` führt auf die Passwortseite, URL wird bereinigt | **erfüllt**                    |
| 5   | `?code=` ohne Verifier erklärt sich                             | **erfüllt**                    |
| 6   | Falsches Passwort ergibt eine deutsche Meldung                  | **erfüllt**                    |
| 7   | Ohne Partner erscheint der Verbinden-Screen, überspringbar      | **erfüllt**                    |
| 8   | Drei Codefehler ergeben drei eigene Meldungen                   | **erfüllt**                    |
| 9   | Verbinden setzt beide `partner_id`, gemeinsame `calendar_id`    | **teilweise** — Konto nötig    |
| 10  | Jahrestag schreibt über die RPC und übersteht einen Reload      | **teilweise** — Konto nötig    |
| 11  | Abmelden räumt alle Schlüssel ab                                | **erfüllt**                    |
| 12  | Mit Abzug und ohne Netz startet die App angemeldet              | **erfüllt**                    |

Neun von zwölf belegt. Drei brauchen ein echtes Konto und ein echtes Postfach;
ihr Code ist vorhanden und gegen Doppelgänger geprüft, aber ein Testdouble
beweist nicht, dass der Server mitspielt.

## 1 — `verify` und `e2e`

```
$ npm run verify
tsc -p tsconfig.json --noEmit     → Exit 0
eslint .                          → Exit 0
vitest run                        → 45 Dateien, 503 Tests, alle grün
vite build                        → ✓ built in 4.04s

$ npm run e2e:live
19 passed
```

`format:check` ebenfalls grün.

**Erfüllt.**

## 2 — Die Wache

Fünf Routen ohne Sitzung geprüft (`e2e/auth.spec.ts`, `ohne Sitzung fuehrt jede
Route auf die Anmeldung`): `/kalender`, `/planer`, `/todos`, `/geld`, `/profil`
landen alle auf `/anmelden` mit sichtbarem `h1`.

Mit Sitzung bleibt die Route (`mit Sitzung bleibt die Route erhalten`): `/geld`
bleibt `/geld`.

Das gemerkte Ziel wird gelesen (`die Anmeldung merkt sich, wohin es gehen
sollte`): nach der Umleitung von `/geld` steht `/geld` im History-State, und ein
Unit-Test führt die Anmeldung von dort auch wirklich dorthin zurück.

Der Ladezustand ist eigens geprüft: solange die Sitzung unbekannt ist, erscheint
**kein** Anmeldebildschirm. Ohne das blitzte er bei jedem Reload auf und die
Route wäre verloren.

**Erfüllt.**

## 3 — Registrieren

**Teilweise erfüllt.**

Geprüft: Der Screen verlangt Name, E-Mail und Passwort, weist ein Passwort unter
sechs Zeichen ab, ohne zu fragen, und führt bei `needsVerification` auf den
Bestätigungshinweis. Das Feld trägt `autocomplete="new-password"`, damit der
Passwortmanager ein neues Passwort anbietet statt das alte einzusetzen.

Nicht geprüft: dass Supabase wirklich eine Mail schickt, dass der Link im
Fragmentteil ankommt (und nicht als `?code=`), und dass er auf einem **anderen
Gerät** funktioniert. Genau das ist die Zusage, für die der Mail-Client mit
Implicit-Flow existiert — sie steht als Umgebungsprüfung unten.

## 4 — Der Recovery-Link

Zwei Playwright-Prüfungen gegen den echten Build:

- `./#access_token=…&type=recovery` landet **nicht** auf `/kalender`, sondern auf
  der Passwortseite oder der Anmeldung. Wichtig, weil der Link eine gültige
  Sitzung trägt: ohne diese Sperre wäre eine weitergeleitete Mail ein Zugang zum
  ganzen Kalender.
- Der Fragmentteil ist danach vom Token befreit (`Token verschwinden aus der
Adresszeile`). Sonst bliebe er in der Chronik und in jedem geteilten Link.

Dazu 22 Unit-Tests auf `parseAuthCallback` — alle vier URL-Formen samt der
Grenzfälle: leerer Fragmentteil, `type` ohne Token, Token ohne
Erneuerungstoken, Fehler und Token gleichzeitig, beide Formen gleichzeitig.

**Erfüllt.**

## 5 — PKCE ohne Verifier

`authErrorKey` bildet die Meldung von `auth-js` („both auth code and code
verifier should be non-empty") auf `authVerifierMissing` ab, und der Text sagt,
was zu tun ist: „Dieser Link lässt sich in diesem Browser nicht öffnen. Fordere
hier einen neuen an." Unit-Test vorhanden.

Der Fall selbst ist in der neuen App selten — die Mail-Links sind Implicit. Er
trifft den OAuth-Rücksprung, wenn jemand ihn aus einer anderen Sitzung öffnet.

**Erfüllt.**

## 6 — Deutsche Fehlermeldungen

Ralia 1.x zeigt `error.message` von Supabase unverändert, auch in der deutschen
Oberfläche. Sieben Fälle haben jetzt eigene Schlüssel; alles andere fällt auf
eine allgemeine Meldung, der Originaltext geht in die Konsole.

| Supabase                             | Ralia 2.0                                    |
| ------------------------------------ | -------------------------------------------- |
| Invalid login credentials            | E-Mail oder Passwort stimmt nicht.           |
| Email not confirmed                  | Diese E-Mail ist noch nicht bestätigt. …     |
| User already registered              | Für diese E-Mail gibt es schon ein Konto. …  |
| Email link is invalid or has expired | Dieser Link ist abgelaufen. …                |
| For security purposes … / 429        | Zu viele Versuche. …                         |
| Password should be at least …        | Das Passwort braucht mindestens 6 Zeichen.   |
| code verifier …                      | … lässt sich in diesem Browser nicht öffnen. |

Im Screen gegengeprüft: falsches Passwort zeigt „E-Mail oder Passwort stimmt
nicht." in einem `role="alert"` — ein gefärbter Kasten allein wird von
Screenreadern nicht angekündigt.

**Erfüllt.**

## 7 — Der Verbinden-Screen

Drei Unit-Tests auf die Weiche: ohne Partner nach `/partner-verbinden`, mit
Partner nach `/kalender`, und ein gemerktes Ziel gewinnt über beides.

Der Screen zeigt den eigenen Code aus der Sitzung, kopiert ihn in die Ablage (mit
Rückfallmeldung, wenn die Berechtigung fehlt) und lässt sich über „Später"
verlassen.

**Erfüllt.**

## 8 — Die Codefehler

| Fall                     | Woher                   | Meldung                                           |
| ------------------------ | ----------------------- | ------------------------------------------------- |
| leer                     | Client, ohne Anfrage    | Bitte geben Sie einen Code ein                    |
| eigener Code             | Client, ohne Anfrage    | Du kannst dich nicht selbst verbinden! 😅         |
| unbekannt                | RPC `invalid_code`      | Ungültiger Einladungscode                         |
| schon verbunden (selbst) | RPC `already_connected` | Du bist bereits mit einem Partner verbunden       |
| Ziel schon verbunden     | RPC `partner_taken`     | Dieser Code gehört zu einem bereits verbundenen … |
| kein eigenes Profil      | RPC `profile_not_found` | Fehler beim Profil. Bitte melde dich erneut an.   |

Der letzte ist eine Berichtigung: `migrations/018` wirft `profile_not_found`,
`partner.js` der Altversion kennt es nicht und meldet „Einladungscode ungültig" —
was etwas Falsches behauptet.

Nur zwei Prüfungen liegen im Client, und beide nur, weil ihre Antwort ohne
Anfrage feststeht. Einen **fremden** Code kann der Client nicht auflösen: die
SELECT-Policy auf `profiles` gibt nur die eigene und die Partnerzeile heraus.

**Erfüllt.**

## 9 — Verbinden

**Teilweise erfüllt.**

Geprüft: Der Aufruf geht mit dem normalisierten Code an `connect_partner`; eine
leere Antwort ohne Fehler gilt **nicht** als Erfolg (sonst hielte sich die App
für verbunden und hätte `partner === null`); nach Erfolg schreibt der Provider
Profil, Partner und die gerechnete `calendar_id` fort, ohne einen zweiten
Rundlauf, der scheitern könnte.

Nicht geprüft: dass die RPC in der Datenbank wirklich beide Zeilen setzt und die
Events umhängt. Das ist Migration 018 und war schon vor diesem Umbau live —
aber es ist nicht _hier_ belegt.

## 10 — Jahrestag

**Teilweise erfüllt.**

Geprüft, und zwar gezielt: der Aufruf benutzt `p_date`. Das ist der Parameter,
den die Funktion wirklich trägt — die Typen sagten jahrelang
`p_anniversary_date`, und PostgREST löst RPC-Argumente über den Namen auf. Der
Aufruf wäre zur Laufzeit gescheitert, mitten im Jahrestag. Ein Test wacht jetzt
darüber. Ein leeres Feld schickt `null`, nicht `''`.

Nicht geprüft: dass der Wert nach einem Reload aus der Datenbank zurückkommt.

## 11 — Abmelden

`clearAuthData` räumt ab, und ein Test prüft jede Gruppe einzeln:

- alles mit `sb-`-Präfix oder `supabase` im Namen
- `googleAccessToken`, `googleEmail`, `googleAutoSync`
- `ralia:identity`
- die Offline-Zwischenspeicher `ralia:event-cache:`, `ralia:event-queue:`,
  `ralia:todo-cache:`, `ralia:todo-queue:` — bleiben sie liegen, sieht der
  nächste Nutzer an diesem Gerät die Termine des vorherigen

Was **bleibt**, ist ebenso geprüft: `ralia:theme` und `appLanguage`. Sie sind
Einstellungen des Geräts, nicht der Person; ein Abmelden, das die Sprachwahl
mitnimmt, wirkt wie ein Fehler.

`signOut` benutzt `scope: 'local'` wie Ralia 1.x — eine globale Abmeldung würde
auch das Telefon des Partners aus der Sitzung werfen, wenn dort dasselbe Konto
läuft.

**Erfüllt.**

## 12 — Start ohne Netz

Vier Unit-Tests auf `restoreSession`, und die E2E-Suite hängt selbst daran: ihr
Seed legt Sitzung und Abzug in den Speicher und schneidet jeden Netzweg ab. Alle
neunzehn Tests laufen also durch genau diesen Pfad — die Regel „nur eine echte
Abmeldung meldet ab" wird bei jedem Lauf mitgeprüft, nicht umgangen.

Die Gegenrichtung ebenfalls geprüft: online und keine Sitzung heißt wirklich
abgemeldet. Würde der Abzug auch dort retten, käme ein abgemeldeter Nutzer nie
zum Anmeldebildschirm zurück.

**Erfüllt.**

## Abweichungen von der Vorlage

| Stelle          | Vorlage                                      | Hier                                      | Grund                                                                                                                                   |
| --------------- | -------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Auth-Screens    | fehlen                                       | aus der Design-Sprache                    | dieselbe Fläche, Radius 20 px, derselbe Schatten, dieselbe Kicker-Zeile; mittig statt randlos, weil hier keine Navigation am Rand klebt |
| Abmelden        | Wort in „Ralia 2.0 · Datenschutz · Abmelden" | eigener Knopf                             | etwas, das man nur durch Treffen des richtigen Wortes auslöst, ist kein Bedienelement                                                   |
| Fehlermeldungen | englischer Satz von Supabase                 | übersetzte Schlüssel                      | die Oberfläche ist deutsch                                                                                                              |
| Codekollision   | Anlegen scheitert still                      | neuer Code, bis zu fünfmal                | der Nutzer stand sonst ohne Profil da                                                                                                   |
| Einladungscode  | `Math.random`                                | `crypto.getRandomValues`                  | ein Code, mit dem sich jemand in einen fremden Kalender verbindet, ist ein Zugangsmittel                                                |
| Trennen         | `showConfirmation`                           | `ConfirmDialog`, Startfokus auf Abbrechen | gleiche Absicht, aber der Startfokus liegt nicht auf der zerstörenden Handlung                                                          |

Nicht abgewichen wird bei Alphabet und Länge des Einladungscodes. Nutzer lesen
ihren Code heute vor; „R7K2QM" muss morgen dasselbe sein.

## Bekannte Grenzen

- **Die Screens zeigen weiter Demo-Daten.** Echt sind ab SP1 Identität,
  Einladungscode, Partner-Verbindung und Jahrestag. Termine, Todos und Geld
  folgen in SP2 bis SP4.
- **Die Profilkarte in den Einstellungen** zeigt noch `MOCK_PROFILE` — Name,
  E-Mail, Avatar und die drei Kennzahlen. Sie an die Sitzung zu hängen ist ein
  Einzeiler, aber die Kennzahlen brauchen echte Termine, und eine halb echte
  Karte ist verwirrender als eine ganz falsche.
- **Kein QR-Code.** Die Vorlage zeigt an der Stelle einen Platzhalter, und der
  steht hier auch.
- **„Neuer Code" und „Teilen"** in den Einstellungen tun nichts. Beides braucht
  eine Entscheidung, die SP1 nicht trifft: ob ein neuer Code den alten ungültig
  macht (dann fehlt eine Migration) und ob geteilt über `navigator.share` oder
  über einen Link läuft.
- **Nur Chromium in E2E.**

## Offene Umgebungsprüfungen

Keine davon ist eine Codeänderung. Alle brauchen ein echtes Konto und ein echtes
Postfach — und ein zweites Gerät.

1. **Registrieren.** Kommt die Mail? Trägt der Link den Fragmentteil und
   **nicht** `?code=`? Das ist der Beleg, dass der Mail-Client mit Implicit-Flow
   wirkt.
2. **Denselben Link auf einem anderen Gerät öffnen.** Der eigentliche Grund für
   den zweiten Client. Klappt es dort, ist die Regression gegenüber Ralia 1.x
   vermieden.
3. **Passwort zurücksetzen**, ebenfalls über zwei Geräte.
4. **Google-Anmeldung.** Der Rundlauf ist aus dieser Umgebung nicht
   durchspielbar; geprüft ist nur die Rücksprung-URL gegen gefälschte Eingaben.
5. **Zwei Konten verbinden** und danach in beiden nachsehen, dass `partner_id`
   auf beiden Zeilen steht und beide denselben Kalender sehen.
6. **Jahrestag setzen, neu laden.** Steht er noch da?

## Fazit

Neun von zwölf Kriterien belegt, drei brauchen ein Konto und ein Postfach. Die
Anmeldung steht, die Wache greift, der Partner-Weg ist vollständig, und der
Start ohne Netz ist bei jedem E2E-Lauf mitgeprüft.

Zwei Dinge sind unterwegs aufgefallen und behoben, beide hätten später mehr
gekostet: die Schema-Typen beschrieben drei Tabellen falsch und hätten dem
Jahrestag einen Laufzeitfehler eingebaut, und `postgrest-js` wiederholt seit 2.111
jeden Lesezugriff selbst — was den Start ohne Netz auf 7,5 Sekunden zog.
